# Архитектурные решения

## ADR-001: Go и embedded SQLite

Используем Go, SQLite FTS5 через pure-Go драйвер modernc. Отдельная БД каждого проекта снижает риск ошибки фильтра по tenant; служебный каталог не содержит знания. SQLite остаётся локальной: открытые DB/WAL не синхронизируются как файлы. Сравнение: Engram, SQLite documentation, Go diagnostics. C++ даёт больше контроля памяти, но не нужен для первого I/O-bound ядра. Замеры обязательны.

## ADR-002: Неизменяемые версии и причинные родители

Знания, prompts, checkpoints и файлы записываются как события с уникальными ID и ссылками на предыдущие версии. Несколько непогашенных heads означают конфликт. Поступление события идемпотентно; порядок получения не уничтожает предыдущие данные. Обычная правка требует ожидаемую версию, решение конфликта ссылается на все рассмотренные heads. Не называем произвольный last-write-wins безопасной синхронизацией знаний.

## ADR-003: Строгий scope

Группа — граница данных. Shared-память — отдельный проект внутри группы. MCP запускается с фиксированной группой/проектом. ACL проверяется до поиска, graph, cache и sync. Явный перенос заметки между группами создаёт новую запись с provenance. Автоматического продвижения личной памяти в общую нет.

## ADR-004: Retrieval перед сжатием

FTS5/BM25 → расширение по графу → ранжирование → выбор целых фактов/фрагментов → точный подсчёт `o200k_base` → пакет с budget и источниками. Original неизменен. Противоречия помечаются. Если всё не помещается, показывается неполнота, а не незаметное превышение лимита. Этот tokenizer — явная локальная единица измерения, не утверждение о скрытом tokenizer текущей модели Codex.

Кэш привязан к ревизии знаний, query, phase, budget и scope. История промптов и шифрованные файловые события не меняют ревизию знаний. Промпты/результаты инструментов исключены из FTS свидетельств: они не меняют BM25-статистику и не вытесняют документы. Стабильное расположение текста помогает provider prefix cache, но его hit rate отдельно от локального cache hit. Нет автоматически исполняемых инструкций из заметок.

В P7 исходный fixture выявил Recall@5=0.95: точный `product_cache` в длинном документе проигрывал коротким общим записям. Добавлен приоритет совпавшего технического идентификатора с `_` внутри уже разрешённой FTS-выдачи. Вопросы и данные fixture сохранены, повторный Recall@5=1.0. Для обобщения на другие репозитории нужны дополнительные наборы, а не подбор новых весов по этому результату.

## ADR-005: Vault и облачный relay

Облачный сервер хранит зашифрованные события и серверные ACL. Клиент проверяет AEAD и привязку к проекту перед применением. Секреты дополнительно защищены vault-ключом в локальной базе, не входят в FTS/граф/обычный context. Ключи и пароли не записываются в конфигурацию Codex или git. Для перехода на второй компьютер нужны права сервера и ключ проекта. Передача ключа — отдельный контролируемый шаг.

## ADR-006: Поддерживаемая интеграция

MCP SDK вместо собственного неполного JSON-RPC. Hooks только официального формата. Установка создаёт конкретные конфиги и skill, сохраняя существующие файлы; не отключает sandbox, approval или hook trust. Тестовый MCP-клиент проверяет протокол без оплачиваемого вызова модели. Полноценное проксирование всей работы Codex необязательно для реализации памяти и не подменяет реальные возможности hooks.

## ADR-007: Интерфейс

Встроенный локальный web UI, без CDN и обязательного Node runtime. Три области: дерево групп/проектов; редактор/список/граф; контекст и состояние. По уточнению пользователя 2026-10-11 применяется тёмная тема в стиле Codex: фон `#212121`, боковая панель `#181818`, поверхность `#242424`, текст `#ececec`, границы `#383838`, нейтральные светлые основные кнопки. Сдержанные голубые и янтарные оттенки используются для связей и противоречий. Шрифт Windows Segoe UI, код Consolas. Рабочий граф и читаемые заметки — главный визуальный элемент; коммерческий лендинг и декоративные KPI-карточки не нужны. Подписи и ошибки по-русски. Клавиатура, видимый focus, reduced-motion, компактный экран.
# ADR-008: управление из чата и подключение действующего проекта

2026-10-11. Добавлено после первоначальной проверки P7 по запросу владельца. Официальный skill `akasha` использует CLI, поэтому доступен до регистрации проекта и до загрузки проектного MCP. Поддерживаемая форма вызова — `$akasha add` или выбор skill; `/akasha add` может быть текстовым запросом, но собственный slash-dispatcher внутри Codex не обещается. Источники: [Skills](https://learn.chatgpt.com/docs/build-skills), [Slash commands](https://learn.chatgpt.com/docs/cli/slash-commands).

Команда `add` находит проект/группу по каноническому локальному пути. При отсутствии однозначной группы возвращается запрос выбора без регистрации. При повторе сохраняется идентификатор проекта. MCP/hooks добавляются только в проектную конфигурацию с предварительной проверкой и резервным копированием; чужие определения не замещаются. Шаблоны промптов и политика бюджета — версионированные записи проекта, исключённые из автоматического retrieval; они участвуют в checkpoint и шифрованной синхронизации. Подстановка переменных текстовая, без запуска кода. Локальный кэш производных пакетов можно очистить без удаления памяти.

## ADR-009: локальные embeddings в 0.2

Уточнение владельца отменяет отсрочку векторного индекса. Выбрана multilingual-e5-small INT8, 384 компоненты, нативный ONNX Runtime на Windows/Linux. Поиск после установки offline, сторонние API-ключи не требуются. RRF объединяет exact/semantic evidence, одиночные code identifiers ищутся лексически. Поиск не утверждает истинность найденного факта. Измерения и ограничения — LOCAL_RAG.md.

INT8 batch зависел от соседних документов: для повторяемого content-addressed кэша inference выполняет один фрагмент за вызов, с внутримодельной многопоточностью. В onnxer (upstream) loader и cleanup Go 1.26 потребовались узкие исправления; включена локальная MIT-копия, изменения перечислены в third_party/onnxer/AKASHA_PATCHES.md. Python используется только для независимой сверки векторов.

## ADR-010: локальный SQLite и серверный PostgreSQL

PostgreSQL выбран для конкурентного серверного каталога, ACL, аккаунтов и ciphertext-журнала. TimescaleDB обслуживает временные метрики, Alembic — последовательность схемы отдельной ролью. PostgreSQL не требует переноса всех локальных проектов на фоновый DB-сервис: offline-память остаётся отдельными SQLite-файлами. Это разделение по нагрузке/эксплуатации, а не утверждение о безусловном преимуществе одной СУБД по скорости.

Сервер проверен на 10 пользователей и конкурентные записи одного проекта. Метрики отправляются ограниченной очередью и batch; первый временной chunk готовится миграцией. Потери служебной телеметрии видны отдельным счётчиком и не считаются потерей событий памяти. Сессии/пароли/отзыв реализованы без зависимости от облачного IdP.

## ADR-011: ресурсы и кэши

Перед работой рассчитываются CPU/RAM-бюджеты. Ограниченные worker pools и окна импорта; упорядоченные записи SQLite; непрерывные float32-матрицы с общим byte-LRU; актуальность по source/indexed revisions. Context cache key читает только ревизию индекса, не пересчитывает размер всей матрицы. Go heap limit не выдаётся за жёсткий RSS cap нативного runtime. См. PERFORMANCE.md.

## ADR-012: создание и версии skills

Пакет skills — версионированное событие shared-проекта группы. Имя не определяет уникальную версию: hash содержимого сохраняет расходящиеся варианты. Создание по итогу работы отделяет роль агента (осмысленная процедура по подтверждённым результатам) от CLI (детерминированная упаковка/проверка/публикация). Один запрос пользователя запускает полный workflow; создание не вызывает дополнительный внешний LLM API. Provenance содержит исходные revision IDs, skills не входят в retrieval, автоматическая межгрупповая активация отключена.
