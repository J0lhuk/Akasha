# CPU, память и производительность

`akasha resources` возвращает фактические доступные ядра, логические потоки, RAM, размеры рабочих очередей и кэшей. Windows: GetLogicalProcessorInformationEx/GlobalMemoryStatusEx; Linux: системные сведения и cgroup memory. Число ядер из названия CPU не принимается за доступное ОС.

На машине проверки: ОС сообщает 6 физических ядер, 12 логических потоков, 31.9 GiB RAM. Выбраны 4 работника импорта и 4 внутримодельных потока. [Снимок профиля](../reports/resources.json).

## Расчёт ограничений

- Go heap: min(2 GiB, доступная RAM / 4), нижняя граница 128 MiB. `GOMEMLIMIT` имеет приоритет; `AKASHA_MEMORY_MB` — явная настройка. Это мягкий предел Go, не ограничение всего процесса.
- Работники: не больше 4 по умолчанию, не больше половины доступных потоков и бюджета heap / 64 MiB. `AKASHA_WORKERS` ограничивается ресурсами машины.
- Импорт читает/разбирает окна по 2 × workers; запись результатов упорядочена. Очередь не растёт вместе с количеством файлов.
- Матрицы float32 хранятся непрерывно. Общий byte-LRU векторов: min(128 MiB, heap / 8); ключ включает путь проектной БД, модель и обе ревизии. Большая матрица сканируется потоково.
- Для ONNX предусмотрен резерв 512 MiB при планировании; фактическая нативная память находится вне Go heap. Intra-op ≤4, inter-op=1, активное ожидание отключено. Повторно используются ограниченные буферы токенизации, выход ONNX читается без промежуточной копии.
- Поток загрузки модели использует буфер 128 KiB. Встроенный кэш embeddings ограничен 40 000 строками. Context, query embeddings и граф имеют отдельные ключи/правила инвалидации.
- Сервер: пул PostgreSQL 20 соединений, 5 idle; очередь метрик 256, batch 32/100 ms. Счётчик потерь доступен администратору. Хэширование паролей: максимум 2 одновременно, ограниченная очередь и rate limit.

## Проверяемые результаты

На 1000 векторов ×384 точный scan до оптимизации занимал 18.45–21.66 ms; после — 0.92–1.07 ms. Медиана улучшилась примерно в 19 раз. Выделения сократились с ~3.60 MB до ~145 KB на запрос, с 10 766 до 102 аллокаций. Это поиск по готовым векторам, без нового inference. [До](../reports/vector-baseline.txt), [после](../reports/vector-optimized-final.txt).

```powershell
go test ./internal/core -run '^$' -bench BenchmarkVectorScan1000 -benchmem -count 3
.\bin\akasha.exe resources
python scripts/postgres-smoke.py
```

Полные задержки retrieval/context, первоначальная индексация и нагрузка 10 пользователей публикуются отдельно в [VALIDATION](../reports/VALIDATION.md). Нельзя складывать ускорение микробенчмарка с экономией токенов или выдавать его за ускорение всей работы Codex.

SQLite оставлена для отдельных локальных проектов: встроенный offline storage, отсутствие обязательного сервиса, FTS5 и контроль транзакций. Сервер конкурентных пользователей использует PostgreSQL. Для этой нагрузки SQLite не заменяется только на основании названия СУБД; сравниваются конкретные операции и задержки. TimescaleDB хранит временные метрики, а Alembic управляет схемой, они не ускоряют произвольно любой запрос.
