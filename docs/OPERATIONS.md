# Сервер, команда и перенос работы

## Docker hub

Сервер хранит шифрованный журнал событий и каталог разрешений. Ключи расшифровки проектов остаются у клиентов. Локальный UI работает на компьютере; hub не публикует этот UI.

1. На собственном сервере установите Docker и Compose. Скопируйте проект.
2. Создайте `.env` по `.env.example`. Заполните независимые hex-пароли БД, `AKASHA_HUB_TOKEN` и логин/пароль первого администратора. [Процедура PostgreSQL/Alembic и входа](ACCOUNTS_SERVER.md).
3. Выполните:

```sh
docker compose build
docker compose up -d
curl http://127.0.0.1:7342/healthz
```

Compose публикует порт только на loopback. Для другого компьютера настройте ваш HTTPS reverse proxy на `127.0.0.1:7342`, с действительным сертификатом и лимитом тела запроса не меньше 32 MiB. Например, блок для существующего Caddy:

```caddy
memory.example.com {
    reverse_proxy 127.0.0.1:7342
}
```

Замените домен своим. Клиент отказывает в обычном HTTP к нелокальному адресу и не следует редиректам с токеном. Не открывайте backend-порт напрямую в Интернет. Для публичного сервера задайте rate limits на proxy, резервирование и мониторинг диска.

Контейнер запускается UID 10001, с read-only rootfs, отдельным `/data`, tmpfs, ограничением памяти/CPU и без дополнительных capabilities. Каталог данных принадлежит только этому сервису. Внешний сервер в данной работе не развёрнут: проверен настоящий Docker hub локально.

## Подготовка первого компьютера

Переменные окружения задавайте через менеджер секретов или защищённый интерактивный ввод. Примеры ниже предполагают, что переменные уже установлены:

- `AKASHA_VAULT_PASSWORD` — пароль локального vault, минимум 12 байт.
- `AKASHA_HUB_TOKEN` — токен пользователя облачного сервера.
- `AKASHA_KEY_PASSPHRASE` — отдельный пароль переносимого ключа проекта.

Не вводите настоящие значения в историю терминала или промпт агента.

```powershell
.\bin\akasha.exe sync-enroll --project atlas --url https://memory.example.com
.\bin\akasha.exe capture --project atlas --git
.\bin\akasha.exe key-export --project atlas --out E:\Recovery\atlas.akasha-key
.\bin\akasha.exe sync --project atlas --url https://memory.example.com
```

`capture` сохраняет рабочие файлы; `--git` дополнительно сохраняет refs и Git bundle. Git-репозиторий должен содержать хотя бы один commit. Если Git не нужен или история больше лимита, используйте `capture` без `--git` и штатный Git remote для истории.

`import` строит базу знаний, `capture` сохраняет файлы для переноса. Это разные операции. `.env`, ключи, базы, служебные каталоги и Gitignored-файлы автоматически не отправляются; список пропусков возвращается в отчёте. Нужные пароли добавьте в vault отдельно. Проверяйте отчёт перед сменой компьютера.

## Продолжение на втором компьютере

Передайте шифрованный `atlas.akasha-key` и его пароль раздельными доверенными каналами. Локальный пароль vault на втором компьютере может отличаться. Установите переменные окружения для этого компьютера и создайте пустую папку проекта.

```powershell
.\bin\akasha.exe sync-catalog --url https://memory.example.com
.\bin\akasha.exe sync-clone --project atlas --root D:\Work\Atlas --file E:\Recovery\atlas.akasha-key --url https://memory.example.com
.\bin\akasha.exe restore --project atlas
.\bin\akasha.exe restore --project atlas --apply
.\bin\akasha.exe integration --project atlas --out D:\Work\Atlas\.akasha-integration
```

Сначала просмотрите dry-run. Существующие локальные изменения не перезаписываются: входящая версия сохраняется в `.akasha-conflicts`. Нерешённые параллельные версии пропускаются до выбора. Удаления возвращаются как `deletion_pending` и не удаляют файл автоматически.

Для восстановления Git-истории:

```powershell
.\bin\akasha.exe git-export --project atlas --out D:\Transfer\atlas.bundle
git clone D:\Transfer\atlas.bundle D:\Work\AtlasGit
```

Bundle содержит коммиты и refs. Рабочие незафиксированные файлы возвращаются через `restore`, отдельно от Git. Не клонируйте поверх уже заполненной папки.

Общая память группы — свой проект со своим ключом: зарегистрируйте, выдайте доступ и синхронизируйте его отдельно. Каталог сам по себе не содержит знаний и не даёт ключей.

## Пароли проекта

```powershell
# AKASHA_DATABASE_PASSWORD заранее установлен безопасным способом.
.\bin\akasha.exe secret-set --project atlas --name 'database production' --secret-env AKASHA_DATABASE_PASSWORD
.\bin\akasha.exe sync --project atlas --url https://memory.example.com
```

Значение исключено из поиска, wiki, графа и MCP. На другом компьютере пользователь открывает vault и явно раскрывает запись. CLI `secret-get --id <revision> --out <file>` создаёт намеренный открытый экспорт; сохраните его только в подходящее защищённое место.

Пароль vault и переносимый ключ нужно сохранять отдельно. Сервер не может восстановить забытый ключ. Windows DPAPI-токен не копируется на другой компьютер: новый компьютер создаёт собственный локальный токен и импортирует ключ проекта.

## Команда

Серверные пользователи и локальные пользователи — отдельные каталоги. Интерфейс «Доступ команды» управляет локальными правами; для удалённой команды администратор управляет hub:

```powershell
.\bin\akasha.exe hub-user-add --name 'Developer 2' --url https://memory.example.com
.\bin\akasha.exe hub-grant --project atlas --user <user-id> --role editor --url https://memory.example.com
.\bin\akasha.exe hub-grant --project atlas --user <user-id> --role reader --url https://memory.example.com
# Отозвать доступ:
.\bin\akasha.exe hub-grant --project atlas --user <user-id> --role '' --url https://memory.example.com
```

Новый токен выводится один раз. Администратор передаёт токен конкретному участнику и отдельно решает, выдавать ли ключ проекта. Reader может загружать; editor — загружать и отправлять; admin — также управлять правами проекта. Глобальный owner видит все проекты своего экземпляра.

Каждый участник работает в своей локальной папке/worktree. Параллельные правки образуют две версии; они не теряются и не выбираются по времени часов. Разрешение требует всех текущих heads и объяснения. Это не редактор посимвольного совместного ввода.

Отзыв гранта прекращает новые серверные запросы, но не стирает уже скачанные данные. Ключ проекта открывает данные всего проекта, включая его vault; для иной аудитории выделяйте отдельный проект и ключ. Криптографическая подпись индивидуального автора и ротация проектных ключей в этой версии не реализованы.

## Автоматизация, backup и восстановление

UI: после успешного подключения можно включить обмен каждую минуту, пока открыты ключи. Настройка с серверным токеном сохраняется шифрованной. Автообмен переносит события; снимок изменённых исходников и применение файлов остаются явными действиями. Lock vault прекращает последующие автоматические обмены; уже начатый HTTP-запрос может завершиться.

Авточекпоинты памяти создаются после изменяющих CLI-команд, hooks и раз в минуту у работающего UI/MCP. Checkpoint: `<data>/spaces/<group>/projects/<project>/checkpoints/*.jsonl.gz` и соседний `.sha256`. Wiki: соседняя папка `wiki` с manifest. Внешнюю Markdown-правку импортируйте через `wiki-import`; экспорт не затирает изменённую вручную страницу.

```powershell
.\bin\akasha.exe checkpoint --project atlas --reason 'Перед обновлением'
.\bin\akasha.exe restore-checkpoint --project atlas --file D:\Backup\checkpoint.jsonl.gz
```

Для полной локальной резервной копии остановите **только Akasha**, скопируйте весь её data-каталог и vault, затем запустите и проверьте восстановление в отдельный data-каталог. Не копируйте только открытый `.db` без WAL. У hub резервируйте **PostgreSQL согласованным backup плюс `/data`**; не удаляйте volumes командой `down -v`. Подробности в ACCOUNTS_SERVER.md.

Изменение `AKASHA_HUB_TOKEN` или bootstrap-пароля в `.env` после первичной инициализации не меняет существующие учётные данные. Для паролей используйте `hub-account-set`, для отзыва сессий — `hub-sessions-revoke`. Проектные ключи и recovery-token сохраняйте отдельно; их автоматическая ротация не реализована.
