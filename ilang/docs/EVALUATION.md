# Измерения и критерии приёмки

## Текущая реализация

| Механизм | Измеримый критерий | Проверка |
|---|---|---|
| Вопросы перед исполнением | 0 пакетов с планом при незаполненном обязательном параметре или issue | Go + реальный CLI |
| Версии | 0 автоматических выборов из нескольких версий; составной skill сохраняет выбранную версию | Go |
| Типы и зависимости | Ошибки типов, неизвестные входы, циклы и незаявленные эффекты отклонены | Go, отрицательные сценарии |
| Ограничения | Больше 16 уровней / 128 узлов не разворачиваются; пакет ≤ явно заданного бюджета | Go |
| Изоляция | Чужая версия из другой БД не разрешается; reader не записывает и не включает режим | Go |
| Retrieval | 0 skills/запусков в evidence; knowledge revision не меняется | Go |
| Совместная работа | Устаревший ответ не перезаписывает новую ревизию | Go |
| Возобновление | Checkpoint восстанавливает определения и вопросы; флаг остаётся выключенным | Go |
| Анализ | Отчёт связан с хэшем плана; passed требует свидетельства каждого критерия | Go + CLI |
| Извлечение рецепта | Следующий вызов снова спрашивает параметры и вопросы диалога | Go + CLI |
| MCP | 9 tools в обычном режиме / 16 при включении; выключение действует без нового подключения | MCP round-trip |
| Текст MCP | Процедура встречается один раз; полный текст не дублируется в metadata; токены content совпадают с пакетом | MCP round-trip |
| Сборки | Windows amd64 и Linux amd64 компилируются | go build; запуск Windows CLI |
| Производительность | ns/op, B/op, allocs/op для композиции из трёх вызовов и общей проверки | Go benchmark, три повтора |

Команда воспроизведения: `python -X utf8 ilang/validate.py`. Отчёты находятся в `../reports/`; `VALIDATION.md` содержит фактические цифры. Проверочный runner ограничивает GOMAXPROCS четырьмя потоками; это настройка проверки, не изменение обычного профиля ресурсов Akasha.

## Эксперимент качества кодинга — ещё не проведён

Сравнить на одних задачах и моделях:

- A: обычная просьба Codex;
- B: нынешняя память Akasha;
- C: именованный атомарный skill;
- D: композиция с уточнением и проверками;
- E: кандидат ультра метаскилла после отдельного обучения.

Стартовый корпус: 60 задач в трёх семействах (сервис/API, исправление дефекта, изменение данных), с независимыми проверками; разделение по репозиториям на train/dev/test, например 30/15/15. Этого достаточно для пилота и выявления крупных проблем, но недостаточно для узкой статистической гарантии. Для вывода о неухудшении качества рассчитать объём выборки по дисперсии пилота; нельзя обещать доверительный интервал заранее.

Фиксировать входные/выходные токены, токены provider cache, число вызовов, полную стоимость всех неудачных попыток, время человека на вопросы, успех приёмочных тестов, регрессии, нарушения границ группы. Передавать sealed test-набор только независимому оценщику; оптимизатор не меняет вопросы и критерии ради красивого отчёта.

Проектные цели, **не измеренные достижения**: ≥20% сокращения полной стоимости при согласованном уровне качества; ноль утечек между группами; p95 локальной сборки ≤25 мс на фиксированном наборе из 100 определений и 20 узлов. Выбирать победителя по качеству и полной цене, не по длине короткого пользовательского слова.

`total_cost = clarify + normalize + retrieve + compose + execute + verify + repair + optimization/N`.

Если разница стоимости одного запуска до и после оптимизации положительна, `break_even_runs = ceil(optimization_cost / saved_cost_per_run)`. Если разница неположительна, окупаемость не наступает. Счётчик локального кэша не равен скидке провайдера.

Для ультра-режима потребуются отдельные жёсткие пределы кандидатов/итераций/вызовов и независимое принятие версии. В первой реализации оптимизатор отсутствует; доказанная корректность сборки плана не переносится автоматически на корректность сгенерированного серверного кода.
